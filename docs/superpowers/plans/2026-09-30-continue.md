# `--continue` — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a `--continue` CLI flag. After a task fails, the scheduler keeps admitting every task whose transitive dependency closure contains no failure, instead of aborting the run. The run still exits non-zero and now reports **every** failure. Independently of the flag, the failed-run summary stops calling every unexecuted task "downstream" and splits it into **blocked** and **not started**.

**Architecture:** Three separable changes.

1. **Classification (flag-independent).** A pure function over `(scheduledTaskIds, failedTaskIds, getTransitiveDependencies)` partitions the tasks left in `TaskStatus.Scheduled` into blocked and not-started. `TaskScheduler.getTransitiveDependencies` is already public and already holds the full closure, so no accessor needs adding. `ExecutionTracker.notRunCount` is replaced by `blockedCount` / `notStartedCount`, which need the graph and therefore take it as an argument rather than reading a new tracker field.
2. **Admission (`--continue` only).** `TaskPool.pushTask` currently `throw`s after emitting `onTaskFailed`, and that rethrow is what collapses `run()`'s `Promise.all` and drops every not-yet-started task. Under `--continue` the pool records the failure in a `failures: NadleError[]` array and returns normally, so sibling recursions keep going. `TaskScheduler` gains a `markFailed(taskId)` so `getReadyTasks` never hands out a task that has a failure in its closure, and so sequential mode can advance past a main task that can no longer settle.
3. **Reporting.** `renderFailureCounts` and the agent reporter's `summaryLine` take two counts instead of one. The agent reporter's `not-run` token is **removed** and replaced by `blocked` and `not-started` — a deliberate break for output parsers, already recorded in the spec changelog.

**Tech Stack:** TypeScript (ESM, strict, `node22`), vitest (integration-first, `withGeneratedFixture` + `execa`), tsgo/tsup builds, api-extractor for the public API surface.

**Spec:** `spec/03-scheduling.md` § "Failure Handling" (binding), plus `spec/09-cli.md`, `spec/12-error-handling.md`, `spec/13-reporting.md`, `spec/11-events.md`, `spec/14-plugins.md`. The spec is already written, reviewed and merged on this branch at version **4.2.0**. **Do not re-derive it and do not bump the version** — the only spec work left is the 04-execution reconciliation in Task 1.

## Review Focus

Input classes the spec implies but which no single task's happy path exercises. Each is assigned to the task that owns the code.

1. **Diamond dependency.** `d ← b, c ← a`, with `b` failing. `c` must still run under `--continue` (its closure holds only `a`), and `d` must be **blocked**, not not-started, because `b` is in its transitive closure. This is the case that distinguishes "blocked via a direct edge" from "blocked via the closure". Test in Task 6.
2. **Blocked via a blocked intermediate.** `c ← b ← a`, `a` fails. `b` is blocked by the direct edge; `c`'s *only* unmet dependency is `b`, which never failed — it never ran. `c` must still classify as blocked, because the transitive closure of `c` contains `a`. If the implementation reaches for the direct-dependency graph instead of the transitive one, `c` comes out as not-started and this test catches it. Test in Task 6.
3. **`--continue` with real parallelism.** `--continue --parallel --max-workers 2`. The `exec` helper's injected `--max-workers 1` masks every concurrency bug in this feature; the test must override it. Under two workers an independent branch must keep being admitted concurrently with a failure, and the recursion in `pushTask` must not lose a branch. Test in Task 7.
4. **A task that succeeds during a failed `--continue` run still writes its cache entry.** Run with `--continue`, one task fails and a cacheable independent task succeeds; the run exits non-zero. Re-run with only the cacheable task requested: it must report `UP-TO-DATE` / `FROM-CACHE`. Test in Task 8.
5. **Sequential `--continue` across main tasks.** `nadle a b --continue` where `a` fails: `b` must still run and get a verdict. Without the main-task-advance fix in Task 5, `a`'s tree never settles and the scheduler never advances. Test in Task 7.
6. **Fail-fast regression.** The blocked/not-started split applies **without** `--continue`. Every existing default-mode failure must keep failing fast, keep the same exit code, and now report the two counts instead of one. Task 4 rewrites `failure-output.test.ts` for this; no new flag appears in those tests.

```ts
import { type TaskIdentifier } from "../models/task-identifier.js";

export interface FailureClassifierInput {
	/** Tasks scheduled for the run that never reached a terminal status. */
	readonly nonExecutedTaskIds: readonly TaskIdentifier[];
	/** Tasks that failed during the run. */
	readonly failedTaskIds: ReadonlySet<TaskIdentifier>;
	/** Full transitive dependency closure of a task, as the scheduler computed it. */
	readonly getTransitiveDependencies: (taskId: TaskIdentifier) => ReadonlySet<TaskIdentifier>;
}

export interface NonExecutedTasks {
	/** At least one task in the transitive dependency closure failed. */
	readonly blocked: TaskIdentifier[];
	/** No failure anywhere in the closure; the run ended before the task ran. */
	readonly notStarted: TaskIdentifier[];
}

/**
 * Partitions tasks that never ran into blocked and not-started. The two sets are
 * mutually exclusive and jointly exhaustive — see spec/03-scheduling.md.
 */
export function classifyNonExecutedTasks(input: FailureClassifierInput): NonExecutedTasks {
	const { failedTaskIds, nonExecutedTaskIds, getTransitiveDependencies } = input;

	const blocked: TaskIdentifier[] = [];
	const notStarted: TaskIdentifier[] = [];

	for (const taskId of nonExecutedTaskIds) {
		if (hasFailureInClosure(taskId, failedTaskIds, getTransitiveDependencies)) {
			blocked.push(taskId);
		} else {
			notStarted.push(taskId);
		}
	}

	return { blocked, notStarted };
}

export function hasFailureInClosure(
	taskId: TaskIdentifier,
	failedTaskIds: ReadonlySet<TaskIdentifier>,
	getTransitiveDependencies: (taskId: TaskIdentifier) => ReadonlySet<TaskIdentifier>
): boolean {
	if (failedTaskIds.size === 0) {
		return false;
	}

	for (const dependencyId of getTransitiveDependencies(taskId)) {
		if (failedTaskIds.has(dependencyId)) {
			return true;
		}
	}

	return false;
}
```

`hasFailureInClosure` is exported separately because Task 5's admission guard needs exactly the same predicate. Do not duplicate it there.

Note the closure is **transitive**, which is what makes Review Focus item 2 work with no propagation pass: a task blocked only via a blocked intermediate still has the original failure in its own closure.

			.add(notStarted > 0 && `not-started ${notStarted}`)
			.build();

		return `${result} in ${formatTime(this.tracker.duration)} (${counts})`;
	}
```

## Summary

Closes #716. Adds `--continue`: after a task fails, the scheduler keeps admitting every task
whose dependencies all succeeded, instead of dropping everything that had not started.

```bash
nadle lint typecheck test --continue
```

A gate of independent checks now gets a verdict for each of them in one run. The run still
fails — non-zero exit code, every failure reported.

## Behavior

- A task with a failure anywhere in its **transitive** dependency closure is never admitted,
  with or without the flag. Because the closure is transitive, a task blocked only via a
  blocked intermediate needs no separate propagation rule.
- `--continue` changes admission only: no change to dependency order, concurrency, or cache
  decisions. A task that succeeds during a failed run still writes its cache entry, because
  cache writes are gated on the task's outcome, not the run's.
- Sequential mode: a main task is complete once nothing in its tree can be admitted any
  more, so a failure in main task 1 no longer prevents main task 2 from running.
- CLI-only, like `--exclude` / `--watch` / `--dry-run`. Not available via `configure()`.

## Also fixes the reported summary defect

The failed-run summary counted every unexecuted task as "downstream ... not run", which was
wrong for tasks independent of the failure. It now reports two counts, **blocked** (a failure
in the transitive closure) and **not started** (independent of every failure). This applies
with or without `--continue`, so a non-zero not-started count is exactly the signal that
`--continue` would have produced more verdicts.

## Breaking

The agent reporter's `not-run` token is removed and replaced by `blocked` and `not-started`.
Output parsers reading `not-run` need updating.

## Notable

- No new `TaskStatus` and no new events: blocked/not-started are a derived classification of
  tasks left in `Scheduled`, not a status, and such tasks never reach a terminal state.
- Corrects `spec/04-execution.md` § Cancellation, which claimed a failure destroys the pool
  mid-run and cancels in-flight tasks. It does not — teardown is in `run()`'s `finally`, so
  in-flight tasks finish and are reported. Adds the `Canceled` test coverage that was
  entirely missing.
